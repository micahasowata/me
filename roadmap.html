0. Starting Point

  • [ ] Baseline: sophomore CS student, effectively zero prior depth in algorithms, discrete math, or systems. Basic programming exposure only. GitHub is empty — intentionally.
  • [ ] "Starting from zero" means: no assumed prior mastery of proof, complexity analysis, or C++. Every foundational concept is built explicitly, not assumed.
  • [ ] "Success after one year" means: fluent in C++, capable across CLRS through graph algorithms, mathematically mature in discrete math/calculus/linear algebra, functional in Rust, exposed to OCaml, and holding 4+ production-quality GitHub repositories that demonstrate real capability — not activity.

1. Philosophy

Subtract and push. You explore too many books, languages, and paths. This roadmap removes those decisions for you. When you feel the urge to add something — a new book, a new language, a new side-project — the correct action is to write it down and not act on it. The roadmap has already decided. Your job is execution, not curation.

Outwork everyone by being bored. Most people quit at the boring middle of a hard topic — the fortieth CLRS exercise, the twentieth induction proof, the third day debugging a red-black tree rotation. Competence is built exactly there. Treat repetition and difficulty as the terrain, not an obstacle to route around.

Why depth beats breadth. Fifty shallow exposures produce someone who recognizes vocabulary but can't build anything. Five deep competencies produce someone who can be handed an unfamiliar problem and reason from first principles. Your stated long-term goals — compilers, databases, low-latency systems — are all depth disciplines. Breadth-first learning is directly incompatible with them.

Why this roadmap prioritizes foundations. You cannot build a compiler without discrete math (grammars, proofs, induction) and strong programming fundamentals. You cannot build a database without data structures, algorithms, and systems understanding. You cannot write low-latency code without deep C++ fluency, memory-model understanding, and profiling discipline. Every one of your stated interests routes through the same foundation. This year builds that single foundation, deliberately, once.

2. The Rules

  • [ ] No textbook substitutions. PPP3, CLRS, Epp, Stewart, Lay are locked for the year.
  • [ ] No new languages beyond C++, Rust, OCaml. Python for scripting only, never for core learning.
  • [ ] No projects outside the project ladder in Section 7. New ideas go in a notebook, not into active work.
  • [ ] No phase transitions without meeting the written exit criteria for the current phase.
  • [ ] No abandoning a hard topic out of boredom. If stuck, go deeper into that topic — never sideways to something easier.
  • [ ] No reading without implementing. Every algorithm, every proof technique gets written by hand or in code.
  • [ ] No tool shopping. One editor, one debugger, one compiler, one build tool. Master them; stop researching alternatives.
  • [ ] No GitHub activity for its own sake. Only finished, tested, documented work goes public.
  • [ ] No roadmap redesign mid-phase. Record concerns; revisit only at phase boundaries.
  • [ ] No treating "almost finished" as a reason to linger. Ship the current unit of work and move to the next.
  • [ ] No mistaking reading for competence — competence is demonstrated by unaided implementation.
  • [ ] No restarting the roadmap after falling behind. Use the recovery protocol in Section 9 instead.

4. DSA Roadmap (CLRS, C++ Implementation Language) 

CLRS 1-3   | Foundations: algorithm mindset, insertion sort, asymptotic notation
           | Supports: Epp ch.1-3 (logic, proof, induction) — read together
	CLRS 4     | Divide-and-conquer: master method for recurrences
           | Supports: Epp ch.6 (relations) for recurrence structure
	CLRS 5     | Probabilistic analysis: randomization in algorithms
	CLRS 6-9   | Sorting/selection: heapsort, quicksort, linear-time sort, selection
           | Supports: Epp ch.7 (combinatorics) for average-case analysis
	CLRS 10-13 | Data structures: arrays/lists/stacks/queues, hash tables, BST, RB-tree
	CLRS 14-16 | Advanced techniques: DP, greedy, amortized analysis
	CLRS 20-25 | Graph algorithms: search, shortest paths, MST, max-flow, matching
	CLRS 26-35 | Selected topics: NP-completeness (34), approximation (35), survey rest

The explicit chain is: discrete math builds proof ability → CLRS uses proof ability to justify correctness and complexity → C++ implementation makes the algorithm real → problem-solving applies it to new problems. Never implement an algorithm you cannot yet explain the correctness of on paper.

Rules specific to CLRS:

  • [ ] Do not memorize algorithms — understand structure, then implement
  • [ ] Read each core chapter (1–16, 20–25) twice: intuitive pass, then formal pass
  • [ ] Do not implement in multiple languages simultaneously — C++ throughout P1–P4, Rust joins for P5's graph chapters only

5. Mathematics Roadmap

Discrete Mathematics (Epp) — Priority 1

Timing: Phases 1–2, primary focus. This comes first because algorithm correctness and complexity analysis are meaningless without proof technique, induction, and counting.

  • [ ] Ch.1 Logic — propositional/predicate logic, implication, contrapositive
  • [ ] Ch.2 Proof techniques — direct, contrapositive, contradiction
  • [ ] Ch.3 Induction — weak and strong, essential for algorithm correctness proofs
  • [ ] Ch.4 Sets — subsets, power sets, unions, intersections
  • [ ] Ch.5 Counting — permutations, combinations, pigeonhole
  • [ ] Ch.6 Relations — reflexive/symmetric/transitive, equivalence classes
  • [ ] Ch.7–8 Advanced combinatorics and applied algorithmic math (Phase 2)

Applied directly to: CLRS correctness proofs and complexity lower bounds.

Calculus (Stewart) — Priority 2

Timing: Phases 2–5, increasing depth, always secondary to discrete math and DSA. Necessary for optimization reasoning and eventual numerical/graphics work, not urgent in Phase 1.

  • [ ] Ch.1–2 Functions, limits, derivatives (Phase 2, light)
  • [ ] Ch.3–5 Exponential/log functions, differentiation, integrals, fundamental theorem (Phase 3)
  • [ ] Ch.6–7 Integration techniques, applications (Phase 4)
  • [ ] Ch.8–9 Series, parametric equations (Phase 5, light)

Applied to: performance/optimization modeling, later numerical methods.

Linear Algebra (Lay) — Priority 3

Timing: Phases 3–5, increasing depth. Needed for graphics, ML, and some database/systems optimization work — lowest time-pressure of the three in Year 1.

  • [ ] Ch.1–3 Systems, matrix operations, determinants (Phase 3)
  • [ ] Ch.4–5 Vector spaces, eigenvalues/eigenvectors (Phase 4)
  • [ ] Ch.6–8 Orthogonality, symmetric matrices, geometry of vector spaces (Phase 5)

Applied to: future graphics transformations, least-squares fitting, network/matching eigenvalue interpretation.

Sequencing rule: discrete math never competes for time with calculus or linear algebra in Phase 1 — it runs alone. Calculus and linear algebra are introduced only once discrete math foundations (Epp ch.1–5) are solid, and both remain secondary to CLRS and C++ throughout.

9. Weekly Operating System

Normal Week

  • Study (new material): ~7.5 hrs
  • Implementation: ~15 hrs
  • University coursework: ~8 hrs
  • Administration/planning: ~2 hrs
  • Total: ~32.5 focused hours

Busy University Week (exams, heavy HW)

  • Reduce new study to 4–5 hrs (review only, no new topics)
  • Maintain 10–12 hrs implementation to preserve momentum
  • Increase university time to 12–15 hrs
  • Total: ~30 hrs

Recovery Week (post-crunch)

  • 10–12 hrs total, split evenly between review and light implementation
  • No new material
  • Prioritize sleep, exercise, and returning to baseline before resuming normal pace

Recovery Protocol

  • [ ] W | Behind 1 week → catch up within current phase; defer secondary math topics temporarily
  • [ ] W | Behind 2+ weeks → defer one secondary topic entirely to a lighter phase; prioritize C++/CLRS/discrete math; never restart the roadmap
  • [ ] W | Ahead of schedule → do not skip phases; deepen current phase work instead

15. The Contract

  1. PPP3, CLRS, Epp, Stewart, and Lay are the only primary resources for this year. No substitutions.
  2. C++, Rust, and OCaml are the only languages, activated in that order and never simultaneously as primaries.
  3. Only the six projects in Section 7 are active work. New ideas go in a notebook, not into your week.
  4. No phase transition without every exit criterion in that phase checked off.
  5. When a topic is hard, you go deeper into it — never sideways to something easier.
  6. Every concept gets implemented or proved by hand before it counts as "learned."
  7. One editor, one debugger, one compiler, one build tool — for the entire year.
  8. Only finished, tested, documented code is published to GitHub. Everything else stays private.
  9. The roadmap is not redesigned mid-phase. Concerns get written down and addressed at phase boundaries only.
  10. Falling behind triggers the recovery protocol in Section 9 — never a restart.
  11. Interview preparation does not begin before Phase 6.
  12. Competence is demonstrated by unaided implementation, not by having read the material.
  13. Every week, you can name the single next box on the roadmap without hesitation.
  14. If you break a rule, you write down why before continuing.
  15. Subtract and push. Outwork everyone by being bored.

16. Daily Operating Principle

Every day, before you open a book or an editor, answer one question:

What is the next box?

Find it in the current phase. Check it when done. Move to the next box. That is the entire operating system.

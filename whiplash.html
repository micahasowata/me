Then what — a compiler, a distributed KV store, microservices?

The roadmap builds the substrate. Each step swaps in a new language on purpose — OCaml for the compiler, Rust for the store, JS for the frontend — because each gap is best closed in the language built for it, not by forcing everything back into C++.

Compiler

strong overlap

Transfers directly

  • Recursion & tree traversal → reused almost verbatim for ASTs
  • Hash tables → symbol tables
  • Graphs → control-flow analysis, dependency graphs
  • Finite automata / regular languages (Phase 6) is lexer theory, already covered

Still missing

  • Parsing theory — recursive descent, LL/LR grammars
  • Lexer/tokenizer construction
  • Type systems and type checking
  • IR design, register allocation, optimization passes
Resource: Real World OCaml, read before you write a line of the compiler. OCaml's algebraic data types and pattern matching are close to a perfect fit for ASTs and type checkers — a genuinely stronger substrate for this than C++. Build the compiler in OCaml, not just after reading about it. Your recursion-heavy phases (4, 5, 7) already prime the functional instincts this needs.

Distributed KV store

new discipline

Transfers directly

  • Hash tables → the core lookup structure, now sharded
  • B-trees (Phase 6) → your storage engine
  • File I/O reps → write-ahead logging groundwork
  • C++ ownership/RAII discipline (Phase 2, 4) → maps almost directly onto Rust's ownership model

Still missing — basically a new field

  • Networking / RPC
  • Consensus — Raft, Paxos
  • Replication and partitioning
  • Consistency models — CAP, linearizability vs eventual
  • Failure detection, log-structured storage design
  • Rust itself — ownership, borrowing, lifetimes as the compiler enforces them
Resource: The Rust Book, then build the store in Rust rather than C++. Manual RAII discipline is exactly what Rust's borrow checker formalizes, so this reads more like a stricter dialect of what you already know than a new paradigm. Pair with a from-scratch Raft implementation — the book won't teach you consensus, only the language to build it safely in.

Full-stack, microservices

two languages, one gap

Transfers directly

  • Almost nothing, honestly — this roadmap is single-process and in-memory throughout

Closed by the resources below, not by this roadmap

  • HTTP/REST, a web framework — Let's Go
  • Frontend fundamentals — Eloquent JS
  • Real database layer, migrations — Let's Go Further
  • Auth, middleware, deployment — Let's Go Further
  • Containerization, service discovery, message queues — still open, microservices proper is a further step past a single Go service
Resources: Eloquent JavaScript for the frontend half — real JS fundamentals rather than framework-cargo-culting. Let's Go and Let's Go Further (Alex Edwards) for the backend half — a real Go HTTP service built from scratch: routing, middleware, a real database layer, auth, deployment. Between the two, this card's whole "still missing" list gets covered on purpose, in languages suited to each half rather than forced through C++.
